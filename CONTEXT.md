## Features

### Recipe index (NEI-style)
- Panel with a grid of every item (vanilla and from other mods), with a search box.
  `@modname` filters by mod, e.g. `@terraria` or `@calamity`. Right clicking the search box clears it.
- **Left click** an item: its recipes. **Right click:** the recipes it is used in.
- Each recipe shows:
  - The result.
  - The ingredients: green if you have enough in your inventory, blue if enough is in the chests of a terminal in
    reach, red if not.
  - Groups like "Any Wood", with the icon cycling through the group's members.
  - The crafting stations, with their icons.
  - The conditions (near water, etc.).
- Items that can't be crafted show **How to obtain** instead: NPC shops (with price and conditions), enemy drops
  (with the enemy's sprite, chance, conditions and where it spawns from its Bestiary entry, including drops shared by every enemy) and bags/crates/presents (clickable).
  Built lazily by `Common/SourceDatabase.cs` from `NPCShopDatabase` and `Main.ItemDropsDB`. Chest loot, fishing and
  world drops aren't in any database, so they only get a generic hint.
- Navigation: ingredients and stations are clickable, there is a **Back** button with history, and the mouse
  wheel over the right panel switches recipe.
- Above the grid, one tab per item category (`Common/ItemCategories.cs`, first matching rule wins: accessory, armor,
  tool, weapon/ammo, placeable, consumable, material, misc). Used by both the index and the terminal.
- The item grid is paginated (`UI/ItemGrid.cs`): only the current page is drawn, uncached item textures load at
  most 16 per frame, and lowercase names are cached for the search. Footer: first/previous/page bar/next/last;
  wheel turns pages (Shift: 10), dragging the bar jumps on release.
- Esc closes the index (when not typing in the search box).
- **Tree** tab (`RecipeView.DrawTree`): crafting tree of the recipe on the current page, computed by
  `Common/CraftingPlan.cs`. Owned items come from a shared pool (inventory only), so branches don't count the same
  stack twice; recipe groups accept any member. Intermediates use their first recipe with no ingredient that loops
  back: already on the current path, or itself crafted from the item (reversible recipes like Wood <-> Wood Platform,
  which the path check alone would accept). Items with no such recipe are base materials. Depth capped at 40.
  Recomputed every 30 ticks while shown. Rows: tree (indented), missing materials added up, crafting stations.
- **Crafting goal** (`Common/CraftingGoal.cs`): "Set as goal" in the Tree view stores the item and recipe page in
  `GoalPlayer` (saved with the character as an item tag, so modded goals survive ID changes; dropped if the mod is
  removed). `GoalSystem` recomputes the plan every 30 ticks, draws the missing materials while the inventory is
  closed, and says in chat when everything is ready. The panel is dragged by its title and folded with its -/+
  button; position and folding are saved in `GoalPlayer` and clamped to the screen. Rows and visibility are in
  `ClientConfig`.
- **Crafting from the chests** (`RecipeView.DrawCraftRow`, `TerminalSystem` "Crafting" section): while the last
  used terminal is in reach (`TerminalSystem.CanCraft`; `Terminal`/`HasTerminal` survive closing the panel), the
  recipe view shows how many crafts the chests allow and Craft / x10 / Max buttons. Stations count if they are in
  `Main.LocalPlayer.adjTile` (refreshed with `AdjTiles()` every 30 ticks, since vanilla only does it with the
  inventory open) or on the network's wire: `StorageNetwork.Walk` collects station tiles (`RecipeDatabase.IsStation`)
  into `StorageSnapshot.Stations`, sent in the first `Contents` chunk, expanded with `RecipeDatabase.Provides`
  (vanilla Hellforge -> Furnace, Mythril Anvil -> Anvil, Alchemy Table -> Bottle + Table, Bewitching Table -> Table,
  plus `ModTile.AdjTiles`). Stations and conditions are checked by the client, like vanilla crafting; the server
  (`TerminalSystem.Craft`, `Craft` packet with `Recipe.RecipeIndex`) only takes the ingredients out of the chests,
  all or nothing (`StorageNetwork.TakeIngredients`), creates the result (random prefix, like vanilla) and hands it
  out through the door (`Deliver`), then replies with `CraftResult`. Ingredients come only from the chests.
  Not done: Alchemy Table ingredient savings and mods' `OnCraft` hooks.
- **Take missing** (`RecipeView.DrawTakeRow`): `TerminalSystem.MissingIngredients` works out, on the client, what
  the chests must hand over so the inventory covers 1 craft (Shift: 10), counting owned items once across
  ingredients and accepting any group member (`RecipeDatabase.AcceptedItems`, listed item first). Sent as a
  `TakeItems` packet (type, amount pairs, max 30); the server withdraws them in stacks and delivers them through
  the door like any withdrawal.
- **Compare** (`RecipeView.CompareRows`): header button adds the current item (max 3, oldest dropped) and opens the
  comparison: stats table (rows only where some item has a non-zero value; best in green, lower is better for use
  time and mana) plus each item's tooltip lines wrapped to the panel. Right click an item there to remove it.
- **Keys** (rebindable in Controls):
  - `N`: open or close.
  - `[`: recipes of the hovered item.
  - `]`: uses of the hovered item.

### Storage terminal
- The **Steampunker** sells it for **1 platinum** by default (`ServerConfig.TerminalPriceGold`; it has no recipe).
- **4x2** tile (screen on the left, garage door on the right) that can only be placed on a **background wall**, like a painting (`AnchorWall`).
  If the wall is removed, it drops.
- The **red wire** is walked starting from the terminal's 8 tiles, collecting the chests and crafting stations it
  passes through (capped at `ServerConfig.MaxWireTiles`, 50,000 by default).
- **Right clicking** the terminal opens the panel with the search box already focused.
  - It shows the items from every connected chest, with quantities summed.
  - It refreshes every half second.
- **Clicking** an item: the panel closes, the server takes up to one stack out of the chests (same prefix only), the
  garage door rolls up, the item drops out and the door closes again. Every player sees the door.
- **Right clicking** an item picks up an amount, like taking from a vanilla slot: +1 per click, and holding it repeats
  faster and faster (`TerminalState.UpdateSelection`), capped at what is stored and one stack. It is only a selection
  on the client, drawn on the cursor; the next click on any item withdraws that amount. Right clicking empty space
  in the panel drops it. (Replaced the 0.3 "how many?" pop-up, `AmountPrompt`, on 2026-10-22.)
- **Shift + click** an item: the panel closes, the chests holding it glow gold for 10 s (light and particles), and a
  chat message says how many chests it is in.
- A **gold arrow** on the screen edge points to each highlighted chest that is off screen, with the distance in blocks.
- **Ctrl + click** an item: opens its recipe in the index.
- **Deposit items** button: 20 chest-like slots below the inventory (`DepositState`, Shift + click from the inventory
  via `TerminalPlayer`). On close they go into the chests (matching stacks first, then empty slots) and the door opens.
  Leftovers stay in a `TerminalEntity` (tile entity saved with the world), with a chat warning; they are retried every
  2 s and can be taken back out. Only one player at a time can have a terminal's slots open (lock on the server).
- Chests are found from any of their tiles (vanilla `FindChestByGuessing` only matched the left column).
- When the deposit slots close, each item is drawn flying from the player into the door (other players see it too).
- Closes with Esc (when not typing), the X button, or by walking away (`ServerConfig.TerminalReach`, 10 blocks by
  default).
- **Deposit all** button (`TerminalSystem.QuickDeposit`): the client takes main inventory slots 10-49 (no hotbar,
  coins, ammo or favorites) out of the inventory, syncs those slots and sends the items in a `QuickDeposit` packet.
  The server deposits them and gives back with `QuickSpawnItem` whatever doesn't fit, or everything if the request
  is refused (rate limit, distance), so nothing is lost.
- **Sort** button: name, amount, rarity, mod (`TerminalSort`, ties by name). Resets to `ClientConfig.DefaultSort`
  on world load.

### Portable terminal (`Content/Items/RemoteTerminalItem.cs`)
- Recipe: Terminal + 10 Luminite Bars at the Ancient Manipulator.
- Right clicking a terminal while holding it stores the terminal's top-left corner and `Main.worldID` in the item
  (saved with the item, sent with `NetSend`, so the server knows it; links from other worlds are ignored).
- Using it opens the terminal with `Remote = true`: no distance limit while the player carries a linked portable
  terminal. The server allows requests when `RemoteTerminalItem.CanReach` (within 20 blocks, or carrying a linked
  portable terminal); the deposit-slot lock uses the same check.
- More than 30 blocks from the terminal, withdrawn items appear next to the player (`QuickSpawnItem`) instead of
  dropping out of the door, and deposited items don't fly across the screen.
- In multiplayer the client may not have the terminal's tiles loaded, so in remote mode only the server checks
  that the terminal still exists.

### Settings (`Common/Configs.cs`)
- `ClientConfig` (per player): goal panel on/off and rows; default terminal sort; chest highlight seconds;
  whether "Deposit all" includes the hotbar; delivery drones and chest effects on/off.
- `ServerConfig` (host, synced): Terminal price in gold (applied in `SteampunkerShop.ModifyActiveShop`, so no reload
  needed), reach in blocks (the panel closes beyond it; the server allows reach + 10 for lag), max wire tiles
  walked, and whether portable terminals work (`RemoteTerminalItem.IsLinkedTo` returns false when off).
- Labels and tooltips: `Configs.*` keys in both localization files; enum values as `Configs.TerminalSort.*.Label`.

### Multiplayer
- The client asks the **server** for the contents, since the server is the only one that knows every chest and wire.
- The server scans the network and replies with totals and chest positions per item. Large replies are split into
  packets of about 30 KB.
- Server-side checks:
  - There must be a real terminal at that position.
  - The player must be within reach + 10 blocks, or carry a portable terminal linked to that terminal
    (`RemoteTerminalItem.CanReach`).
  - At most one request every 10 ticks per player.
- Withdrawals, deposits, crafting (`Craft`) and "Take missing" (`TakeItems`) also run on the server; it replies
  with `DepositResult` / `CraftResult` for the chat messages.
- Single player uses the same code, computed locally.
- The mod must be installed on the server and on the clients.

### Performance (for low-end PCs)
- Terminal refreshes (every 0.5 s while a panel or the craft row is shown): the server keeps a hash of its last
  reply to each player (`StorageSnapshot.Hash`, order-independent) and sends nothing when the contents didn't change.
  Opening a terminal forces a full reply, and the client keeps asking for one until it arrives, so a request
  dropped by the rate limit can't leave the panel empty.
- `StorageNetwork.Scan` reuses its wire walk (chests + stations) for 60 ticks per terminal. Withdrawing, depositing
  and crafting always walk the wire again, so they never act on a stale chest list.
- Client `TerminalSystem.Apply`: the stored list (and `Version`, which makes the panel rebuild its grid) only
  changes when the totals do, and one `Item` per type is reused (`itemCache`) instead of running `SetDefaults` for
  every stored type on every refresh. `InReach` is worked out once per update.
- Recipe view: the craft / "Take missing" rows are recomputed every 10 ticks or when the recipe or the chests change
  (not every frame); tree rows are built once per plan; comparison rows (tooltips word-wrapped) only when the
  compared items, the panel width or the language change.
- Crafting goal: the plan is recomputed only when the goal or the inventory (hash of type + stack) changes.
  `CraftingPlan` memoizes its "is this ingredient made from the item" check, cleared when recipes are rebuilt.
- Already cheap before: the item grids only draw the visible page and load at most 16 textures per frame; names
  and categories are cached for the search.

### Index next to the terminal (0.7, instead of idea 35)

- Opening the recipe index while the terminal panel is open (its **Recipes** button, Ctrl + click on an item, or
  the keys) puts both panels side by side: the index on the left, the terminal on the right, centered together
  (`UIHelpers.DockLayout`). On screens narrower than about 1400 UI pixels the index gets narrower (down to 680),
  so the recipe side shrinks instead of covering the terminal. Each state works out its own position every update
  (`BrowserState.Layout` docks while `TerminalSystem.PanelOpen`; `TerminalState.Layout` while
  `RecipeIndexSystem.IsOpen`) and only recalculates when that or the screen width changes.
- Once docked, the index opens and closes with the terminal (`RecipeIndexSystem.OpenWithTerminal` /
  `CloseWithTerminal`, called from `TerminalSystem.Open`, `Close` and `ShowDeposit`). Closing the index by hand
  while the terminal is open turns that off until it is docked again; opening the terminal again brings it back.
- Esc while docked is handled by the terminal only, which closes both.
- The user found opening and closing panels tedious, so the terminal now stays open when taking items out (Ctrl +
  click, a click, or a picked amount) and on "Deposit all". Only Shift + click (highlight chests), Esc, X and
  walking away close it. After a withdrawal the contents are asked for again 2 ticks later.

### Comfort (0.7)

- **Delivery to the player:** a withdrawn item (click, picked amount, "Take missing", middle click) only drops out of
  the door when the player is within 3 tiles of it (`DoorPickupReach`). Farther away, since the panel now stays
  open up to the terminal's reach, the drones fly from the chests to the player (following them) and the item is
  spawned on the player when they arrive (`PendingDrop.ToPlayer`, same 28 ticks; the door stays shut). The
  `ChestMoves` packet carries that player (255 = the door). Crafted results still use the door; no drone carries them.
  Beyond `DoorReach` (portable terminal), items still appear next to the player at once.
- **Search focus on open** is optional (`ClientConfig.FocusTerminalSearch`, on by default), because while typing
  the mod's keys don't work.
- **Remembered search:** reopening the same terminal within 30 s keeps the search text, category tab and page
  (`TerminalState.OnActivate` only clears it otherwise).
- **Middle click in the index** (idea 36): on any item drawn in it (grid or recipe), takes a stack (at most what is
  stored) out of the chests of the terminal in reach, through `RequestTakeItems`. It uses the item hovered last frame
  (`RecipeIndexSystem.HoveredItem`) while the mouse is over a panel, so it works for every slot without new hotspots.
  Messages when no terminal is in reach or the item isn't stored.
- Discarded for now: an early, short-range portable terminal.

### Blueprints (0.8)

- **Blueprint** item (`Content/Building/BlueprintItem.cs`): 10 of any wood at a work bench. Right click opens the
  catalog (`UI/BlueprintState.cs`); left click builds. It isn't used up.
- Designs (`BlueprintDesigns.All`, in this order): small house 10x7, two-floor house 12x13, tower 10x19, medieval
  house 24x23 (5 NPC rooms), castle 42x30 (11), pagoda 26x26 (3), wizard tower 14x31 (4), boss arena 40x13. Pictures
  in `docs/blueprints/`.
- **Designs are made in `tools/blueprints/designs.py`** (in code, so roofs are loops) and `python
  tools/blueprints/build.py` checks them (known characters, furniture footprints, what each piece stands on or hangs
  from, and every listed room with the game's room check: flood fill counting the frame, 60-750 tiles, walls behind
  every open cell, light, chair, table, door or platform), draws `docs/blueprints/*.png` and writes
  `Content/Building/BlueprintDesigns.cs`. Don't edit that file by hand.
- Two layers of text rows: tiles and background walls. Characters are **brushes** (`Blueprints.TileBrushes`,
  `WallBrushes`): a piece of the chosen material (`#` block, `-` platform, `D` door, `C` chair, `T` table, `W` work
  bench, `B` bed, `K` bookcase, `L` chandelier, `l` lantern, `c` candle, `O` clock; `w` wall), or a fixed item found by
  its `ItemID` name at runtime with fallbacks (`S` gray brick, `R` `/` `\` red brick and its slopes, `Y` `(` `)` red
  dynasty shingles (or red brick), `U` `[` `]` blue dynasty shingles (or obsidian brick), `d` dynasty wood (or the
  material), `|` wooden beam, `F` fireplace, `n` red banner, `y` dynasty lantern, `b` bottle, `i` torch; walls `s` gray
  brick, `g` glass, `k`/`q` white/blue dynasty). A material without a piece uses plain wood's, then the fixed
  fallbacks; lights fall back to a torch so rooms stay valid. Names that don't exist are skipped (nothing placed, not
  charged). `.` must be empty, `+` is covered by furniture, `' '` is left as it is.
- **Slopes** are named after their solid corner (`SlopeDownRight` = ◢, the left side of a roof). Not checked in game
  yet: if roofs come out mirrored, swap the two shapes in `TileBrushes`.
- Catalog: one button per design, the materials as item slots, a small preview, the cost in two columns (green = in
  the inventory, blue = the rest is in the chests of a terminal in reach, red = missing), **Take missing** (through
  `TerminalSystem.RequestTakeItems`, so the drones bring it) and **Place**, which closes the catalog.
- While the item is held, `BuildSystem.PostDrawTiles` draws the house see-through with the material's item icons,
  its bottom row on the tile under the mouse and centered on it, with a green border, or red cells and border where
  something is in the way (any tile except grass and plants, which are cleared, or a player where a block goes).
- Blueprints are text rows (legend in `Blueprints.cs`): `#` block, `.` background wall, `-` platform, `_` platform
  with no wall, `D`/`C`/`T`/`i` door, chair, table, torch (top-left cell), `+` the rest of a piece of furniture. Every
  room is valid NPC housing (at least 60 tiles with the frame, walls, a torch, a chair, a table, a door or platforms).
  They were checked with a script (footprints, door and furniture supports).
- Materials are found in the recipes when they load (`Blueprints.FindMaterials`): any solid block with a house
  wall (not a fence), a platform, a door (1x3), a chair (1x2) and a table (3x2) made from it (recipes with exactly one
  block among their ingredients), plus the work bench, bed, bookcase, chandelier, lantern, candle and clock when
  vanilla makes them from it. Vanilla pieces are matched by their exact tile and size (so dressers and toilets don't
  count); modded doors, chairs and tables by their housing sets and size, so modded woods work too. Wood comes
  first, then by name.
- Cost (`Blueprints.Cost`): items already in the inventory are used as they are; the rest are paid with the
  ingredients of their recipe (the one a material's piece was found with, otherwise the first that isn't made back
  from the item), one level deep, with no crafting station needed. Background walls already in place aren't charged
  (or replaced). `Blueprints.Allocate` shares owned items between the lines, exact items first and
  then group lines ("Any Wood" for torches).
- Building: the client checks the place and the materials, takes them out of its inventory (synced) and, in
  multiplayer, sends a `Build` packet with what it used. The server (or single player) checks the place and the
  distance (60 tiles) again, then `Blueprints.Place`: clears grass, places background walls, then blocks, platforms
  and beams (setting slopes), then furniture (`TileObject.CanPlace` at the piece's TileObjectData origin), then 1x1
  objects like torches and candles (they go on walls and tables), frames the area and sends it in tile squares of
  at most 30x30. If it fails the materials are spawned back on the player. `BuildResult`
  tells the builder; on success a puff of smoke and a sound.
- Sprite: `Content/Building/BlueprintItem.png`, 28x28, a blue sheet with a grid and a white house, rolled on
  wooden rods.

### Goal "next step" button (0.7, idea 35 as the user chose it)

- Above the goal panel's list, a green button crafts the next step towards the goal: "Craft 3 x Iron Bar", then
  "Craft 1 x Iron Broadsword". `GoalSystem.FindStep` walks the plan's tree children first and takes the first
  crafted node that can be made now: its ingredients are in the inventory (every child is a base material fully
  owned) and its station is nearby (`adjTile`, or the wire of a terminal in reach), or else the chests of a terminal
  in reach have them (`TerminalSystem.MaxCrafts`, then `RequestCraft`). It makes the node's `Crafts`.
- From the inventory, `GoalSystem.TakeFromInventory` removes the ingredients (all or nothing, any group member,
  synced with `SyncEquipment`) and the result is spawned on the player with a random prefix, like the terminal's
  crafting. No Alchemy Table savings or `OnCraft` hooks (idea 37).
- If no step can be made but one has its ingredients and lacks only its station, the row says which station.
- Every refresh (30 ticks, while a goal is set) calls `AdjTiles()` (vanilla only does it with the inventory open)
  and refreshes the terminal's contents when in reach. After a click the button is greyed out for 45 ticks so a
  double click doesn't craft twice.

### Delivery drones and chest effects (0.7, ideas 38 and 39)

- `StorageNetwork` records every chest an item type went into or out of (`Moves`, one `ChestMove` per chest, type
  and direction, at most 16). After each withdrawal, deposit (including the automatic retries), craft and "Take
  missing", `TerminalSystem.ShowMoves` hands them to `NetworkEffects` (single player) or sends a `ChestMoves`
  packet to every client (server).
- `NetworkEffects` (client only, just for show): taken out, the chest sparks (electric dust bursting out, a cyan
  light for 20 ticks and a high `Grab` sound, once per chest) and a drone flies the item to the door in 24 ticks.
  Put in, after the items fly from the player into the door (`FlyTicks`), drones carry them to the chests, which
  spark (dust falling in, a lower sound) when they arrive. No drone for chests more than 60 tiles from the door, and
  nothing at all more than 120 tiles from the player.
- To let the drone arrive first, a withdrawn item now drops 28 ticks after leaving the chests instead of 14
  (`DeliveryTicks`), and the door starts rolling up 14 ticks before. This is on the server, so it doesn't depend on
  the client's settings: with drones off the item simply comes out about a quarter of a second later.
- Drone sprite: `Content/Storage/DeliveryDrone.png`, 20x28, two 14 px frames (rotors spinning), facing right and
  flipped when flying left. The carried item hangs from its claw. Both effects can be turned off in `ClientConfig`.

### Languages and in-game help (0.7, ideas 40 and 41)

- Localization files for every language tModLoader supports: `de-DE`, `fr-FR`, `pt-BR`, `ru-RU`, `it-IT`, `pl-PL`,
  `zh-Hans` (written by Claude, not reviewed by native speakers). They avoid naming vanilla NPCs and items in the
  text; the tip after placing a terminal gets the Red Wrench's and the Mechanic's names from the game
  (`Lang.GetItemNameValue`, `Lang.GetNPCNameValue`), so they always match.
- `UI/HelpButton.cs`: a "?" button whose hover tooltip lists the panel's controls (`HelpTerminal`, `HelpIndex`).
  The terminal's is left of "Deposit all"; the index's is left of its X.
- First-time tips in chat, saved per character in `TerminalPlayer` (`SeenPlaceTip`, `SeenOpenTip`): after placing
  the first terminal (`TerminalTile.PlaceInWorld`), how to connect it; after opening one, where the help and the
  Recipes button are.

### Radio (0.6, a joke item the user asked for on 2026-10-22)

- 2x1 floor tile like the Piggy Bank, crafted at an anvil (8 Wood, 3 Iron/Lead Bars, 2 Glass).
- Two clips the user supplied (`Content/Sounds/RadioSiu.mp3`, `RadioLosDos.mp3`, ID3 tags stripped; tModLoader
  decodes mp3 sounds with MP3Sharp). `RadioSystem` plays them alternately: 3-15 s after a radio appears, then gaps of
  10-40 s (35%), 40-90 s (45%) or 90-150 s (20%) after each clip. The server (or single player) runs the schedule,
  so everyone hears the same clip at the same time: it collects each player's nearest radio that is on (within
  60x40 tiles) and sends them in a `RadioPlay` packet; each client plays the clip once, at the nearest of those.
  Clip lengths are hard-coded (`ClipTicks`) because a dedicated server doesn't load sounds.
- Right click toggles on/off: `TileFrameX` +36 (frames 2-3 are the dark dial), sent to the server with the
  `RadioToggle` packet in `TerminalNet` and synced with a tile square. Turning it off stops a clip that is playing.
  `GetItemDrops` is overridden because the off frames would otherwise count as a style with no item.
- While a clip plays, each client spawns the music box's note gores (570-572) by the antenna, about one every
  20 ticks.
- Sprites are generated pixel art (red body, speaker grille, dial, knobs, antenna).

## How to build and test

1. Install **tModLoader** from Steam and launch it once.
2. Copy or link `TerraIndex/` into `Documents\My Games\Terraria\tModLoader\ModSources\`.
3. In tModLoader: **Workshop → Develop Mods → TerraIndex → Build + Reload**.
4. For multiplayer: Host & Play with the mod enabled, and have another player use the terminal on chests they
   have never opened.
5. Go through [`TESTING.md`](TESTING.md), one section per feature.

Coming from the old name: remove the `ModSources\RecipeIndex` link, create `ModSources\TerraIndex`, disable any old
`RecipeIndex` in the mod list, and rebind the keys.
